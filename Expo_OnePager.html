Problem Statement

Battery Drain After Key-Off

  • After key-off, select ECUs continue transmitting NM messages, holding the CAN bus awake beyond the allowed timeout window.
  • Sustained bus activity exceeding 50 mA of parasitic current leads to dead-battery complaints and repeat warranty claims.
  • Manual log review across large traces (1,000–2,700+ messages, 50 ECUs) is time-consuming, error-prone, and inconsistent between engineers.
  • No standardised tooling exists within the team to triage NM violations from raw .asc / .csv logs without specialist software licences.

Proposed Solution

Automated NM Violation Analyser

  • A self-contained HTML/JavaScript tool that parses ASC (Vector CANalyzer) and CSV/TXT NM log files directly in the browser — no server or install required.
  • Automatically classifies each ECU as Normal, Slow, Violation, or Stuck Awake against configurable thresholds.
  • Generates a per-ECU timeline chart with a key-off marker, making evidence immediately legible for design reviews and fault reports.
  • Exports results as CSV or JSON for attachment to JIRA / DOORS or inclusion in warranty investigation reports.

Analysis Workflow

Step 01 Load Log Drag & drop or paste ASC / CSV / TXT
Step 02 Configure Set key-off time, NM timeout, max wake limit
Step 03 Analyse Automatic classification of all ECUs
Step 04 Report Export CSV / JSON or print for review

ECU Status Definitions

StatusMeaningAction
NORMAL Slept within NM timeout (≤5 s default) No action
SLOW Slept within max wake time, but late Monitor — review NM tuning
VIOLATION Exceeded max wake time before sleeping Investigate NM configuration
STUCK AWAKE Never entered sleep mode in log window Critical — root cause required
Typical root causes for STUCK AWAKE: pending UDS diagnostic session (0x10 02), incomplete OTA download, stuck NM state machine, or external wakeup via LIN sub-bus.
